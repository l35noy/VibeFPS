# GEMINI.md — правила разработки и стандарты проекта VibeFPS

Этот документ является каноническим набором правил и стандартов разработки проекта VibeFPS для Gemini / Antigravity.

---

## 1. Базовые принципы разработки

1. **Язык общения и документации:**
   * Все ответы в диалоге, документация, комментарии к коду и пояснения пишутся **исключительно на русском языке**.
2. **Коммиты и Git:**
   * **Коммитит только пользователь.** Агенту категорически запрещено самостоятельно вызывать `git commit`, `git push`, `git reset --hard` или менять историю Git.
   * Агент может запускать только информационные команды (`git status`, `git diff`), а также `git mv` при согласованном перемещении файлов. В конце выполненной задачи агент предлагает пользователю понятный текст сообщения для коммита.
3. **Чистота файловой системы:**
   * **Никаких файлов вне проекта:** запрещено создавать временные файлы, логи или дампы в пользовательском профиле ОС, на рабочем столе или во внешних папках.
   * **Чистый корень `res://`:** в корне проекта запрещено создавать `.tscn` сцены и `.gd` скрипты. Корень зарезервирован исключительно под `project.godot`, иконку, конфигурации и служебные файлы репозитория.
4. **Принцип малых шагов:**
   * *Маленькая рабочая система → проверка → стабилизация → расширение.*
   * Не писать абстракции «на будущее», не усложнять архитектуру и не переписывать стабильно работающий код без подтверждённой необходимости.

## 2. Стандарты разработки в среде Godot 4.7.2 (GDScript)

1. **Статическая типизация:**
   * Весь код на GDScript обязан использовать явную строгую типизацию: сигнатуры функций (`func take_damage(amount: float) -> void:`), переменные (`var speed: float = 5.0`), возвращаемые типы и типы аргументов сигналов.
   * Избегать нетипизированного `Variant` везде, где тип заранее известен.
2. **Читаемость и структура кода:**
   * Имена переменных и функций — `snake_case`, имена классов и типов — `PascalCase`, константы — `SCREAMING_SNAKE_CASE`, приватные методы и поля — с префиксом `_`.
   * Сложная или нетривиальная логика (математика векторов, физические расчёты, навигация) снабжается понятными поясняющими комментариями на русском языке.
   * Докстринги (`##`) используются для описания экспортируемых параметров (`@export`) и публичных методов API.
3. **Архитектурный принцип связности (Call Down, Signal Up):**
   * Родительские узлы могут вызывать методы своих прямых дочерних узлов.
   * Дочерние узлы **никогда не обращаются к родителям напрямую** — передача информации наверх происходит строго через **сигналы** (`signal`).
4. **Безопасность узлов и ссылок:**
   * Проверять валидность динамических объектов через `is_instance_valid()`.
   * Не полагаться на жёсткие пути в дереве узлов (`$../../Node`), предпочитать `@onready @export var` или доступ по группам и контрактам.
   * Код должен быть устойчив к автономному запуску: если синглтон автозагрузки отсутствует (например, в изолированном headless-тесте), скрипт должен использовать безопасный fallback, а не падать с `null reference`.

## 3. Модульная структура папок (Co-location)

Все новые файлы раскладываются строго по функциональным компонентам в соответствии с канонической структурой:

```text
res://
├── core/                  # Автозагрузки и системные синглтоны (GameState, SaveSystem, InputGate)
├── entities/              # Сущности (персонаж, враги, их материалы и скрипты)
│   ├── player/            # Сцена игрока, player.gd, материалы тела
│   ├── enemies/           # Враги (подпапки по видам: contact, flying, boss)
│   └── common/            # Общие компоненты сущностей (hurtbox.gd)
├── weapons/               # Оружие, снаряды и контроллеры (подпапки: pistol, auto, projectile)
├── levels/                # Локации и арены (lobby, range, локации Фазы 4+)
├── ui/                    # Интерфейс, HUD, панели инвентаря
├── data/                  # Ресурсы параметров .tres (data/weapons/, data/enemies/)
├── tests/                 # Автоматические тесты сцен и подсистем
├── tools/                 # Скрипты тестирования и автоматизации (run_checks.ps1)
└── docs/                  # Документация (ровно 3 файла)
```

## 4. Архитектурные инварианты VibeFPS

1. **Смена сцен:** строго через [`GameState`](file:///e:/projects/VibeFPS/core/game_state.gd) (`enter_location` / `return_to_lobby`). Прямой вызов `get_tree().change_scene_to_file()` внутри игровых сцен запрещён.
2. **Гейт ввода:** управление персонажем, стрельба и взаимодействие (E) разрешены только при захваченном курсоре мыши (`InputGate.is_play_input_allowed`).
3. **Слои коллизий (Collision Layers):**
   * 1: `world` (статическая геометрия)
   * 2: `player_body` (тело игрока)
   * 3: `enemy_body` (тело врага)
   * 4: `enemy_hurtbox` (зона получения урона врагом)
   * 5: `projectile` (снаряды оружия)
   * 6: `interactable` (точки взаимодействия: магазин, двери)
   * 7: `player_hurtbox` (зона получения урона игроком)
4. **Физика и снаряды:**
   * Темп физики: 120 Гц (`physics/common/physics_ticks_per_second = 120`), Jolt Physics 3D.
   * Снаряды — дискретные `Area3D` на скорости 70 м/с. Хитбоксы персонажей и врагов не могут быть тоньше 0.5 м во избежание туннелирования.

## 5. Документация и тестирование

1. **Каноническая документация (ровно 3 файла):**
   * [`docs/PROJECT.md`](file:///e:/projects/VibeFPS/docs/PROJECT.md) — архитектура, геймплейный канон, стек, константы.
   * [`docs/CHECKLIST.md`](file:///e:/projects/VibeFPS/docs/CHECKLIST.md) — актуальный статус задач, пройденные проверки, открытые вопросы.
   * [`docs/ROADMAP.md`](file:///e:/projects/VibeFPS/docs/ROADMAP.md) — дорожная карта будущих этапов.
   * *Запрещено создавать промежуточные брифы и отчёты задач в репозитории.*
2. **Тестирование:**
   * Единственная точка входа тестов: `pwsh -File .\tools\run_checks.ps1`.
   * Пункт в чеклисте помечается выполненным `[x]` только после реальной проверки (зелёный тестовый сьют или подтверждённый ручной запуск).
   * Любая новая механика должна сопровождаться соответствующим тестом в папке `tests/`.
