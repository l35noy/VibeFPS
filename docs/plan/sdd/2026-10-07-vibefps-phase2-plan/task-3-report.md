### 1.1 `scripts/enemy_contact.gd`

API ровно по брифу: сигналы `health_changed(current, maximum)` и `died()`,
`@export var data: EnemyData`, `@export var contact_interval: float = 1.0`,
методы `health()`, `is_alive()`, `take_damage(amount)`.

Ключевые решения (все с русскими «почему»-комментариями в коде):

1. **Слои в `_ready()`, не в сцене** — `collision_layer = _LAYER_ENEMY_BODY` (`1 << 2`),
   `collision_mask = _LAYER_WORLD | _LAYER_ENEMY_BODY` (`(1 << 0) | (1 << 2)`).
   Слоя игрока (2) в маске нет намеренно: тела проходят друг сквозь друга,
   касание ловится хитбоксами (спека §6.3). В сцене слои не заданы вообще.
2. **Детект контакта на стороне врага.** Хитбокс сам себя настраивает через
   `detects_contact = true` (Task 2): monitoring = true, mask = `1 << 6`.
3. **Смерть наблюдаема.** `died` уходит последним в `_die()` — к этому моменту
   враг уже обесцвечен, снят с коллизий и имеет 0 HP, поэтому подписчик видит
   труп, а не ещё живое тело с нулевым здоровьем. Затем 0.2 с обратного отсчёта
   и `queue_free()`.
4. **Материал дублируется в `_ready()`** (урок `range_target.gd`): общий SubResource
   перекрасил бы всех врагов из одной сцены. Боевой цвет берётся из `data.color`.
5. **Цель — по группе `"player"`** (`get_first_node_in_group`), без путей в сценах.
6. **Непригодные данные выключают врага:** `push_error` + `set_physics_process(false)`
   в `_ready()`, до первого обращения к `data`. `_max_health` копируется в `_ready()`,
   чтобы `health_changed` оставался вызываемым даже при `data == null`.
7. **Контактный тик:** `_on_hurtbox_area_entered` (зона 1) → **немедленный** тик +
   запуск аккумулятора; `_physics_process` → `acc += delta`, тик при
   `acc >= contact_interval`, `acc -= interval`; `area_exited` → сброс.
   Урон всегда `data.contact_damage`, не захардкоженная десятка.
8. `set_deferred("monitoring", false)` в `_disable_collisions()` — обязателен, код
   приходит из обработчика сигнала, который движок зовёт в проходе обновления
   пересечений (тот же контракт, что в `projectile.gd`).

Порядок в `_die()`: флаги → обесцвечивание → выключение коллизий → таймер → `died.emit()`.

## 4. Что именно проверяет моя секция (70 утверждений)

Всё грузится из сцен: `load("res://enemy_contact.tscn").instantiate()` + `is_node_ready()`;
мир вокруг (пол, стена) — программно, как в `tests/projectile.gd`. Снаряды — настоящий
`res://projectile.tscn`, урон наносится только через попадание снаряда в хитбокс
(нигде нет прямого `apply_damage` в обход сцены).

- **Сцена и класс:** корень `CharacterBody3D`, `class_name ContactEnemy`, наличие API
  `health/is_alive/take_damage/died/health_changed`.
- **Данные:** `data` типа `EnemyData`, путь именно `res://data/enemies/contact.tres`,
  `max_health == 50.0`, `contact_damage == 10.0`.
- **Слои (проводка сцены + спека §6.3):** тело `1 << 2`, маска тела `(1<<0)|(1<<2)`
  (игрока нет); хитбокс `zone == 0`, `detects_contact == true`, после готовности
  слой `1 << 3`, `monitoring == true`, маска `1 << 6`; у хитбокса есть `CollisionShape3D`.
- **Материал:** узел `Mesh`, есть `material_override`, два инстанса одной сцены
  получили **разные** материалы (дублирование), живой враг покрашен в `data.color`.
- **Старт:** `health() == 50.0`, `is_alive()`, `contact_interval` по умолчанию 1.0.
- **Непригодные данные:** `data = null` и `is_valid() == false` → `push_error`,
  `health() == 0.0`, `not is_alive()`, `is_physics_processing() == false`, узел
  переживает 20 тиков без падения.
- **Сквозная проводка снаряд → слои → хитбокс → враг:** попадание именно в хитбокс
  врага (не в пол, не в стену) → `health() == 20.0`; второй снаряд → `died` ровно
  один, `health() == 0.0`, `is_alive()` ложь, в момент сигнала `died` уже 0.0 и мёртв.
- **Смерть:** материал близок к `Color(0.5, 0.5, 0.5)` (допуск 0.01) — «теряет цвет»;
  `collision_layer == 0`; хитбокс перестал обнаруживать; урон по мёртвому не
  испускает `died` повторно и не двигает здоровье; тело убрано со сцены не сразу
  (проверка «через ~0.2 с, а не мгновенно»).
- **Два снаряда, одна цель, один кадр (усиленная редакция):** каждый снаряд
  предъявляет `hit_something` с именем хитбокса врага; оба попадания пришлись на
  **один физический кадр** (проверено сравнением `Engine.get_physics_frames()`);
  `died` ровно 1; `health() == 0.0` ровно; `is_alive()` ложь; в момент `died` 0.0;
  оба снаряда кончились и убраны со сцены. Проверка не может пройти, если оба
  снаряда промахнулись, — каждый снаряд обязан назвать цель.
- **Контактный тик** (`contact_interval = 0.1`, перекрытие с игроком из `player.tscn`):
  игрок стоит на полу и в группе `"player"`; **два гварда из решения контроллера** —
  хитбокс игрока `monitoring == false` и `collision_mask == (1 << 0)`
  (детект на стороне врага, спека §6.3); 9 тиков по 10 → игрок жив с 10.0 HP;
  десятый тик → `died` ровно один, в момент сигнала 0.0 и мёртв, затем респавн
  до 100.0 (контракт Task 2); урон за тик взят из `data.contact_damage`.
- **Каденция и мгновенность:** задержка первого тика от входа ≤5 тиков
  (интервал 0.1 с = 12 тиков при 120 тиках/с — с запасом различимо); разброс между
  тиками не хуже 1 тика от расчётных 12. Наблюдение: реальные тики приходят на
  `[104, 117, 129, 141, 153, 165, 177, 189, 201]` — 12–13 тиков, потому что
  накопление `delta` даёт 12.999… вместо ровно 13; допуск ±1 покрывает это и
  отличает каденцию от «тика каждый кадр».
- **Обрыв контакта:** враг отведён на 6 м (`area_exited`, симулируется позицией),
  30 тиков (2.5 интервала) — здоровье игрока не убывает, игрок жив. Затем враг
  возвращён, и десятый тик убивает игрока.

## 7. Опасения и для решения владельца

1. **Счётчик полного прогона: 9, а не 10** (раздел 5). Нужен тринадцатый элемент в
   `$Tests` раннера либо подтверждение, что ожидание было неточным. Правку не вносил.
2. **Мутация (c) краснеет не на «два снаряда … died ровно один»**, а на «урон по
   мёртвому врагу не испускает died повторно» (раздел 3). Обе проверки ловят один
   гвард; если ревью требует, чтобы именно двухснарядная гонка падала на снятом
   `is_alive()`, нужно добавить в неё урон **после** смерти — это изменение
   проверки, а не реализации, и я его не делал без решения.
3. **Слои не заданы в `.tscn` — только в `_ready()`.** Так требует бриф («правило
   проекта»), но в инспекторе сцена покажет слои по умолчанию, пока узел не в дереве.
   Если владелец хочет видимость в редакторе, это осознанное исключение из правила,
   и оно должно быть в сцене, а не возвращаться неявно.
4. **`push_error` в зелёном прогоне.** Сценарий непригодных данных намеренно
   производит две строки ERROR. Код возврата они не трогают, но в логе раннера

## F1. Различающая проверка «урон берётся из `data.contact_damage`»

**Замечание (дословно смысл):** бриф требует «Тестовый урон берётся из

**Что изменено — только `tests/enemies.gd`, функция `_test_enemy_contact_tick`.**
Игровой код не тронут: `scripts/enemy_contact.gd`, `enemy_contact.tscn`, `player.gd`
и `tools/run_checks.ps1` побайтово те же.

1. **Сценарий ведётся на нестандартном уроне.** Перед спавном врагу подставляется
   **дубликат** `EnemyData` с `contact_damage = 7.5` (`enemy.get("data").duplicate()`
   → `probe.contact_damage = 7.5` → `enemy.set("data", probe)`). Дубликат, а не правка
   `contact.tres`: ресурс читают разделы Tasks 1–2, и правка на месте утекла бы в них.
   При 7.5 захардкоженная десятка не может совпасть ни с одним производным числом.
   Новое **предусловие** печатает оба числа и падает, если подстановка не сработала:
   ```
   [PASS] precondition: сценарий контакта идёт по НЕСТАНДАРТНОМУ урону за тик, а не по 10.0 из contact.tres
          (contact_damage 7.5000, урон contact.tres 10.0000)
   ```
2. **Все ожидаемые числа выведены, а не зашиты.** Из `data.contact_damage` и
   `player.max_health`:
   - `ticks_to_death = ceil(max_health / contact_damage)` = `ceil(100/7.5)` = **14**;
   - `survivable_ticks = ticks_to_death - 1` = **13** (вместо жёстких «девяти»);
   - `health_before_death = max_health - survivable_ticks * contact_damage` = **2.5**
     (вместо жёстких `10.0`);
   - `interval_ticks = round(contact_interval * 120)` = **12** — из экспорта врага,
     раньше литерал «12 тиков» был зашит в подпись и в сравнение;
   - граница «первый тик на входе» — `maxi(2, interval_ticks / 2)` = 6 вместо 5
     (тик по расписанию опоздал бы на целый интервал, тик на входу приходит за 1 кадр).

   ```
   урон за тик 7.5000, HP игрока 100.0, тиков до смерти 14, на границе остаётся 2.5000
   тики контакта: [115, 128, 140, 152, 164, 176, 188, 200, 212, 224, 236, 248, 260] (интервал 12 тиков)
   ```
3. **Новая проверка урона за каждый тик**, а не только на границе. В цикле опроса
   считается худшая ошибка `|прошлый HP − текущий HP − contact_damage|`, и она

   ```
   [PASS] урон КАЖДОГО тика равен data.contact_damage, а не захардкоженному числу
          (худшая ошибка за тик 0.0000 при уроне 7.5000)
   ```
   Именно эта проверка ловит подмену в первом же тике, тогда как сумма за N тиков
